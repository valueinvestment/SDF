# 엔지니어링 의사결정 기록 — SDF Digital Twin

이 프로젝트의 엔지니어링 결정들을 서브시스템별로 망라적으로 정리한 문서다. 각 항목은 동일한 구조를 따른다: **왜 필요했는가** / **안 했으면 어떤 문제가 있었는가** / **개발 후 무엇이 개선됐는가**. 여기 적힌 모든 내용은 이 저장소의 실제 파일·커밋·테스트로 추적 가능하다 — 시스템 다이어그램은 [`docs/ARCHITECTURE.md`](./ARCHITECTURE.md), 플러그인 플랫폼 절의 전체 설계 이력(설계 문서 13개, 구현 계획 17개)은 `docs/superpowers/specs/` / `docs/superpowers/plans/`를 참조한다.

**이력서 문장(XYZ 공식)으로 바로 옮기기 좋게 가장 강력한 항목만 추린 짧은 버전은 [`docs/RESUME_HIGHLIGHTS_TOP.ko.md`](./RESUME_HIGHLIGHTS_TOP.ko.md)에 있다.**

---

## 이 프로젝트는 무엇인가

공장 플로어를 실시간 3D로 시뮬레이션하는 디지털 트윈(Next.js + Three.js 프런트엔드, FastAPI + asyncio 백엔드, 영속 WebSocket)이면서, 이상 감지 시 Claude 3-에이전트 체인(진단→배차→RICE 의사결정)을 가동하고, 노코드 비주얼 빌더(드래그앤드롭 엔티티, 커스텀 GLB 모델, 자유 그리드 레이아웃)를 제공하며 — 가장 큰 작업 단위로 — 서드파티가 호스트 앱을 포크하지 않고 프런트엔드/백엔드 양쪽을 확장할 수 있는, 보안을 진지하게 고려한 플러그인 플랫폼을 처음부터 구축했다. 총 커밋 249개 중 177개가 플러그인 플랫폼이며, 9개 로드맵 Phase에 걸쳐 매 태스크마다 2단계 리뷰(스펙 준수 → 코드 품질)와 Phase별 최종 홀리스틱 리뷰를 거쳐 만들어졌다. 전체 테스트 스위트: 243개(프런트엔드 Vitest 169개, 백엔드 pytest 74개) 전부 통과.

## 1부 — 핵심 실시간 아키텍처

### 1.1 하나의 React 트리 대신 3개로 격리된 렌더링 레이어

**왜 필요했는가:** 이 앱은 16ms 프레임 예산을 두고 경쟁하는 근본적으로 다른 갱신 주기를 3개 갖고 있다 — 3D 로봇 위치는 10Hz로 도착하고, 센서 차트는 매번 다시 그리지 않아도 살아있는 느낌이 나야 하며, 에이전트 패널은 이산적 이벤트에서만 바뀐다.

**안 했으면 생겼을 문제:** 10Hz 위치 업데이트를 (상태관리 라이브러리를 거치더라도) React 상태에 쓰면 쓸 때마다 React 재조정(reconciliation)이 발동한다. 로봇 여러 대 기준 10Hz면 초당 수십 번의 트리 재조정이 Three.js 자체의 `requestAnimationFrame` 루프와 같은 프레임 예산을 두고 직접 경쟁하게 되어 눈에 보이는 끊김이 생긴다.

**개발 후 개선된 점:** 로봇 위치는 React/Zustand를 완전히 우회한다 — `useWebSocket`이 `useRef`(`robotPosRef`)에 직접 쓰고, Three.js 애니메이트 루프가 그 ref를 읽는다. 위치 업데이트로 인한 **React 리렌더 0회** — 코드에서 직접 검증 가능하다(위치 쓰기가 `useState`/Zustand를 전혀 거치지 않음). 센서 차트는 반대로 Zustand를 구독해서 업데이트마다 다시 그린다 — ECharts 자체의 Canvas 렌더러를 쓰기 때문인데, 여기서 요구된 건 모든 곳에서 리렌더를 없애는 게 아니라 두 독립 렌더러를 서로 격리하는 것뿐이었기에 위치 파이프라인보다 의도적으로 더 단순한 경로를 택했다.

### 1.2 Next.js API 라우트 대신 독립된 FastAPI 백엔드

**왜 필요했는가:** 이 앱은 영속 WebSocket 연결과 계속 도는 10Hz 시뮬레이션 루프, 그리고 3~8초 걸릴 수 있는 Claude API 호출이 필요하다.

**안 했으면 생겼을 문제:** Vercel 서버리스 함수는 10초 실행 제한이 있는데, 공교롭게도 이 앱에 필요한 Claude API 타임아웃 예산과 거의 정확히 겹치면서 여유가 전혀 없고, 서버리스 함수는 WebSocket을 무기한 열어두거나 요청 사이에 백그라운드 루프를 돌릴 수도 없다.

**개발 후 개선된 점:** 하나의 장기 실행 Python 프로세스(FastAPI + `asyncio`, Railway 배포)가 시뮬레이션 루프·WebSocket 게이트웨이·에이전트 오케스트레이터를 하나의 이벤트 루프 안에서 독립된 `asyncio` 태스크로 돌린다 — 스레드도, 서브프로세스도, 실행시간 상한도 없다.

### 1.3 시뮬레이터-소비자 간 직접 함수 호출 대신 pub/sub EventBus

**왜 필요했는가:** 시뮬레이션 루프의 출력에는 속도 특성이 완전히 다른 두 소비자가 있다 — WebSocket 브로드캐스터(절대 지연되면 안 됨)와 에이전트 오케스트레이터(트리거되면 Claude API 호출로 수 초간 블록됨).

**안 했으면 생겼을 문제:** 시뮬레이터가 "모두에게 알림"을 직접 함수 호출로 했다면, 빠른 WebSocket 경로가 느린 에이전트 경로의 지연을 그대로 물려받는다 — 이상이 감지되어 AI 진단이 트리거될 때마다 센서 스트림이 끊기게 된다.

**개발 후 개선된 점:** 구독자별로 별도 `asyncio.Queue`를 주는 `EventBus`가 오케스트레이터에 전용 큐를 준다. 오케스트레이터가 수 초짜리 Claude 체인에 블록되어도 10Hz 브로드캐스트 루프는 영향받지 않는다는 걸 이론이 아니라 실제로 검증했다 — 체인 자체가 독립된 `asyncio.create_task()`로 돌기 때문이다.

### 1.4 ID 접두사 문자열 매칭 대신 명시적 엔티티-카테고리 레지스트리

**왜 필요했는가:** 프로젝트 초기엔 엔티티 타입을 ID 접두사(`M1`, `R1`)로 추론했다. 사용자가 생성된 ID(`press-1749375234123`)로 자기 엔티티를 배치할 수 있게 되자 접두사 매칭이 매칭할 대상 자체가 사라졌다.

**안 했으면 생겼을 문제:** "이게 머신인지 로봇인지" 알아야 하는 모든 곳 — 프런트엔드 패널 라우팅, 백엔드 상세 스트림 라우팅 — 이 동적으로 생성된 엔티티를 조용히 오라우팅하거나 누락시킨다. `startswith("M")`은 `press-...`를 인식하지 못하기 때문이다.

**개발 후 개선된 점:** 명시적인 `entity_id → category` 레지스트리(백엔드)와 `placedEntities.find(id)?.type` 조회(프런트엔드), 둘 다 `sync_entities` 재조정 메시지로 채워진다 — ID 문자열 형태가 아니라 레지스트리가 라우팅의 주된 근거가 됐다. 백엔드는 아직 동기화되지 않은 엔티티를 위한 레거시 `startswith("M")`/`"R"` 폴백을 의도적으로 남겨뒀지만(제거하지 않음), 앞으로 추가되는 새 엔티티 타입은 접두사 규칙을 맞출 필요 없이 레지스트리를 통해 올바르게 라우팅된다.

### 1.5 증분 추가/삭제 메시지 대신 전체 상태 `sync_entities` 재조정

**왜 필요했는가:** 프런트엔드와 백엔드는 재연결, 순서 뒤바뀐 메시지, 누락된 이벤트를 겪어도 어떤 엔티티가 존재하는지 합의해야 한다.

**안 했으면 생겼을 문제:** 증분 추가/삭제 메시지는 완벽한 전달 순서를 요구한다 — 메시지 하나가 누락되거나 순서가 바뀌면 프런트엔드와 백엔드가 무엇이 존재하는지에 대해 영구히 어긋난 채로 남고, 자가 복구할 방법이 없다.

**개발 후 개선된 점:** 전체 상태 동기화(WS 연결 시 + `placedEntities` 변경 시마다 전송)는 구조적으로 멱등이다 — 페이로드가 최대 20개 엔티티 수준이라 비용이 미미한 대신, 메시지 손실이나 순서와 무관하게 백엔드가 항상 올바른 상태로 수렴한다.

### 1.6 모델 선택: 3-에이전트 체인에 Opus 대신 Claude Sonnet

**왜 필요했는가:** 이상 하나당 순차적인 Claude 호출 3번(진단, 라우팅, 결정)이 필요하고, 각각 깔끔한 구조화 JSON을 안정적으로, 라이브 대시보드에서 반응성 있게 느껴질 만큼 빠르게 반환해야 한다.

**안 했으면 생겼을 문제:** Opus는 이 특정하고 범위가 좁으며 프롬프트가 잘 짜인 추출 작업(고장 분류, 최근접 로봇 라우팅, RICE 스코어링)에서 그에 상응하는 품질 향상 없이 지연만 늘린다 — 사용자가 체감할 이득 없이 비용/지연만 늘어난다.

**개발 후 개선된 점:** Sonnet은 구조화 추출에서 의미 있게 낮은 지연·비용으로 정확도 기준을 만족시켜서, 전체 3-에이전트 체인이 충분히 빠르게 유지된다 — 에이전트당 10초 타임아웃 + 타입 지정된 폴백이 실제 안전망이지, 상시 발동되는 경로가 아니다.

## 2부 — 노코드 빌더 확장

### 2.1 백엔드 파일 저장소 없는 커스텀 GLB/GLTF 모델 삽입

**왜 필요했는가:** 사용자가 내장 머신/로봇 모양뿐 아니라 자기 3D 모델을 파일 업로드 인프라 없이 배치하고 싶어했다.

**안 했으면 생겼을 문제:** 순진한 구현이라면 백엔드 자산 저장소(실제 인프라 비용, 임의 파일 업로드에 대한 실제 보안 노출면)가 필요하거나, 같은 GLTF 파일을 참조할 때마다 다시 파싱해서 GPU 메모리와 로딩 시간을 태운다.

**개발 후 개선된 점:** 모델은 브라우저 메모리 `ObjectURL`/외부 URL로만 로드 — 백엔드 저장소가 전혀 필요 없다. URL 기준 파싱 캐시 덕분에 같은 모델을 두 번 참조하면 한 번만 로드하고 재사용 시 복제한다. 명시적인 `gltfLoadingRef` 가드(진행 중인 엔티티 ID의 `Set`)가 애니메이트 루프가 같은 엔티티에 로드를 중복 발행하는 걸 막는다 — 애니메이트 루프의 매 프레임 재호출이 없었다면 상시 발생했을 실제 경합 상태다.

### 2.2 엔티티 동기화 카테고리 매핑에 넣은 의도적이고 문서화된 예외

**왜 필요했는가:** 커스텀 GLB 모델도 새 코드 경로를 추가하지 않고 기존 센서/상세 스트리밍 파이프라인에 참여해야 했다(그래야 `SensorChart`/`MachineDetailPanel`도 커스텀 모델에서 동작).

**안 했으면 생겼을 문제(그리고 왜 이게 "나중에 처리" 항목이 아닌가):** 겉보기에 자연스러운 수정 — `custom`에 자기만의 `category` 값을 주는 것 — 은 상세 스트리밍을 조용히 깨뜨린다. 백엔드 게이트웨이의 `if/elif`가 `machine`/`robot`만 인식하기 때문에 `custom` 카테고리는 그냥 통과돼서 `get_entity_category()`가 `None`을 반환하고 상세 패널이 아무 에러 없이 빈 화면이 된다. 이건 `ARCHITECTURE.md`에 명시적으로 문서화되어 있다 — 미래의 기여자가 버그 리포트로 재발견하기 전에 미리 적어둔 것.

**개발 후 개선된 점:** 로봇이 아닌 모든 엔티티(커스텀 포함)를 `category: "machine"`으로 매핑하면 백엔드는 커스텀 모델 지원을 위해 **전혀 변경할 필요가 없다** — 기존 머신 파이프라인이 그대로 동작하고, 눈에 안 띄는 함정은 버그 리포트를 기다리는 대신 문서에 적혀 있다.

### 2.3 그리드 레이아웃 매니저를 CSS-Grid span 문자열에서 정수 좌표로 마이그레이션

**왜 필요했는가:** 레이아웃 매니저에 진짜 드래그/리사이즈 인터랙션(`react-grid-layout`)이 필요했는데, 이 라이브러리는 `{x, y, w, h}` 정수로 말하지 CSS-Grid의 `"1 / 3"` span 문자열 형식이 아니다.

**안 했으면 생겼을 문제:** 기존 문자열 형식을 유지했다면 유지보수되는 드래그-레이아웃 라이브러리를 아예 못 쓰거나, 매 인터랙션마다 두 좌표계 사이를 변환해야 해서 off-by-one 버그의 지속적인 원천이 됐을 것이다.

**개발 후 개선된 점:** `LayoutConfig.version: 2`로 깔끔하게 마이그레이션하면서 우아한 폴백을 붙였다 — `importConfig`가 오래된 버전을 감지하면 크래시 대신 v2 기본 레이아웃으로 리셋해서, 기존 공유 링크가 아예 깨지는 대신 레이아웃이 기본값으로 리셋되는 선에서 기능적으로 저하된다. 라이브러리의 deprecated된 `WidthProvider` HOC는 의도적으로 피하고 `ResizeObserver` 기반 `useContainerWidth()` 훅을 썼다 — 프로젝트 다른 곳의 기존 ResizeObserver 사용 패턴과 일관되게(우연이 아니라 명시적 선택으로 문서화됨).

### 2.4 URL vs localStorage 설정 직렬화 전략을 순수·단위테스트된 함수로

**왜 필요했는가:** 커스텀 모델과 자유 레이아웃이 export되는 설정 JSON을 URL에 안전하게 담을 수 있는 크기 이상으로 부풀릴 수 있다.

**안 했으면 생겼을 문제:** 브라우저/서버의 URL 길이 제한을 조용히 넘기면 사용자 입장에서 명확한 실패 모드도 없이 공유 링크가 깨진다.

**개발 후 개선된 점:** `decideSyncStrategy()`를 순수 함수로 추출하고 보수적인 4000자 하한선을 둬서 DOM 없이도 완전히 단위테스트 가능하게 만들었다 — 들어가면 URL, 안 들어가면 `localStorage` 폴백 + 경고 토스트. 전략 결정 자체가 그걸 소비하는 브라우저 API와 분리되어 독립적으로 테스트 가능하다.

## 3부 — 플러그인 플랫폼 (9개 Phase, 177개 커밋)

이 프로젝트에서 가장 큰 작업 — 단일 목적 대시보드를 서드파티 기여자가 프런트엔드 패널·백엔드 데이터 수집기·처리 스테이지를 호스트 앱을 포크하지 않고 추가할 수 있는 확장 가능한 플랫폼으로 전환했다. 동적 코드 로딩이 등장하는 순간 신뢰 경계가 실제로 어디에 있는지에 대한 명시적이고 근거 있는 판단도 포함한다.

### 3.0 프로세스 결정: 모든 태스크마다 2단계 리뷰 + 최종 홀리스틱 패스

**왜 필요했는가:** 9-Phase, 여러 세션에 걸친 프로젝트는 사람 리뷰어가 매 커밋마다 붙어있지 않아도 Phase가 쌓이기 전에 실제 버그를 잡아낼 방법이 필요했다.

**안 했으면 생겼을 문제:** 구현자(사람이든 AI든)의 자체 보고 "완료"는 기본적으로 낙관적이다 — 단일 태스크의 diff 안에서는 안 보이는 문제들(오래된 클로저, unused-symbol 린트 실패, 테스트 사각지대, 태스크 간 상호작용 버그)은 독립적으로 근거를 다시 확인하는 절차가 없으면 그냥 빠져나간다.

**개발 후 개선된 점 — 실증 사례 포함:** 플러그인 플랫폼의 모든 태스크는 스펙 준수 리뷰(코드가 요구사항과 정확히 일치하는지, 더도 덜도 아닌지 확인)와 코드 품질 리뷰(잘 만들어졌는지 확인)를 순서대로 거쳤고, 각 리뷰는 구현자의 보고를 신뢰하는 대신 실제 diff를 다시 읽고 실제 테스트를 다시 돌려서 검증했다. 이 프로세스가 잡아낸, 확인 안 했으면 그대로 나갔을 실제 버그들 — 대표 사례만 추리면:
- Phase 0: `subscribe` 바인딩이 스토어 직접 접근을 누출하던 문제, 내장 패널 ID 충돌 시 orphan 등록, read-only 스냅샷이 라이브 스토어와 가변 참조를 공유하던 문제.
- Phase 3a: 트레일링 콤마 하나가 플러그인 등록 배열을 조용히 `undefined` 구멍으로 만들던 버그, 감싸지지 않은 `ENOENT`가 원시 크래시로 노출되던 문제, 존재 확인과 파일 쓰기 사이의 TOCTOU 갭, 3개 실패 분기 중 2개만 커버하던 롤백 경로(모든 개별 태스크가 이미 리뷰를 통과한 뒤 최종 전체-브랜치 리뷰에서만 발견됨).
- Phase 4.5: 형태 검사 누락 — 첫 번째 잘못된 형식의 플러그인 파일에서 백그라운드 플러그인 로더 태스크 전체가 조용히 죽었을 버그.
- Phase 5b(가장 최근이자 가장 시사하는 바가 큼): 개별 태스크 리뷰가 실제 버그 3건을 잡았다(ESLint를 깨뜨리는 미리 추가된 미사용 심볼, 컴포넌트 자신의 페이로드 작성 로직을 실제로는 검증하지 않던 드래그앤드롭 테스트 목, 이미 활성화된 UI 탭을 다시 클릭하면 입력 중이던 내용이 조용히 사라지던 데이터 손실 버그). **4번째 버그는 개별 태스크 리뷰로는 전혀 안 보였고 전체 브랜치 diff에 대한 최종 홀리스틱 리뷰에서만 발견됐다**: 룰의 대상 머신을 편집 도중 재지정해도 이미 입력된 조건식이 새 스코프 기준으로 재검증되지 않아서, 자기 머신 스코프에 존재하지 않는 변수를 참조하는 룰이 에러 표시 하나 없이 영구히 발동 불가능한 채로 저장될 수 있었다. 첫 직관적인 수정(검증을 다시 호출)은 실제로는 작동하지 않았을 것이다 — React의 상태 업데이트는 비동기라서 검증 클로저가 여전히 업데이트 전 값을 읽었을 것이기 때문이다. 실제 수정은 새 스코프를 컴포넌트 상태에서 읽는 대신 명시적 인자로 전달해야 했다 — 겉보기엔 맞아 보이지만 조용히 틀린 "수정"을 하기 딱 좋은, 바로 그런 종류의 미묘한 타이밍 버그였다.

### 3.1 스토어 직접 접근 대신 화이트리스트 플러그인 컨텍스트

**왜 필요했는가:** 플러그인은 라이브 센서 데이터를 읽고 UI를 등록해야 하지만, 호스트 내부 아무 곳이나 접근할 수 있어선 안 된다.

**안 했으면 생겼을 문제:** 호스트의 Zustand 스토어나 React 내부에 직접 접근하면 모든 플러그인 작성자가 안전한 플러그인을 짜기 위해 호스트 앱 내부 형태 전체를 독립적으로 이해해야 하고, 호스트 리팩터링 하나가 모든 플러그인에 파괴적 변경이 된다.

**개발 후 개선된 점:** `PluginContext`는 활성화 시점에 정확히 `store.getState`/`store.subscribe`/`registerPanel`/`registerRule`/`registerMetric`만 노출하고, 렌더되는 패널은 그보다도 더 좁은 `PluginProps`(읽기용 `useStoreSlice`, 그리고 실제 필요가 생겼을 때만 추가된 플랫폼 최초의 쓰기 메서드 `setDemoMode`)만 받는다. 이 화이트리스트 계약만 지켜지면 호스트 내부 상태 형태는 자유롭게 바뀔 수 있다.

### 3.2 데이터 수집을 브로드캐스트 루프에서 분리 (Collector/PipelineStage 분리)

**왜 필요했는가:** 실제 데이터 수집기(Modbus, OPC-UA, REST 폴링)는 느리거나 불안정할 수 있는데, 기존 10Hz 브로드캐스트 루프가 그것들에 좌우돼선 절대 안 된다.

**안 했으면 생겼을 문제:** 느리거나 멈춘 실기기 폴링을 10Hz 브로드캐스트 루프 안에서 직접 await했다면, 센서 하나가 불안정한 것 때문에 연결된 모든 클라이언트의 라이브 대시보드 전체가 멈췄을 것이다.

**개발 후 개선된 점:** 각 `Collector`는 자기 주기로 독립된 백그라운드 태스크를 돌며 공유 캐시에 쓰고, 브로드캐스트 루프는 그 캐시를 읽기만 한다. Collector 하나가 오프라인이 되면 시스템 전체가 멈추는 대신 우아하게 저하된다(마지막 정상값 유지, 3회 폴링 실패 후 명시적 `"offline"` 상태 전환). 이건 코드베이스에 이미 있던 `detail_loop`/`simulation_loop` 분리 패턴과 동일한 것 — 재발명하지 않고 알아보고 재사용했다.

### 3.3 플러그인 패널용 렌더-바이패스 선택자 훅 (`useStoreSlice`)

**왜 필요했는가:** 플러그인 패널은 10Hz로 갱신되는 스토어를 구독한다. 순진한 구독은 패널이 실제로 관심 있는 데이터가 바뀌었든 아니든 매 tick마다 리렌더를 일으킨다.

**안 했으면 생겼을 문제:** 머신 하나의 히스토리를 보는 차트 플러그인이, 완전히 무관한 다른 머신의 센서 값이 바뀔 때도 초당 10번 리렌더됐을 것이다 — 핵심 아키텍처(1.1)가 애초에 막으려 했던 바로 그 안티패턴이 아무도 이 지점을 막지 않았다면 플러그인 경계에서 재발했을 것이다.

**개발 후 개선된 점:** `useStoreSlice`는 `useSyncExternalStore`를 선택자 기반 깊은 동등성 메모이제이션으로 감싸서, 패널이 실제로 선택한 값이 바뀔 때만 리렌더된다 — 플러그인 작성자가 이유를 몰라도 화이트리스트 API가 내장 컴포넌트와 동일한 렌더-바이패스 보장을 받는다.

### 3.4 두 동적 로딩 Phase를 관통한 위협 모델 결정

**왜 필요했는가:** 사용자가 던져넣은 파일에서 런타임에 플러그인을 로드할 수 있게 되면(프런트엔드 `.js` 업로드, 백엔드 `.py` 디렉터리 폴링) — 빌드 시점에 리뷰된 소스코드에서만 로드하던 것과 달리 — "이 화이트리스트가 정말로 보안 경계인가"라는 질문에 정직하게 답해야 한다.

**안 했으면 생겼을 문제(가상이 아닌 실제 위험):** 같은 realm의 `import()`는 호스트의 JS realm을 완전히 공유한다 — `activate(ctx)`에 뭘 넘기든 `window`, `document`, 프로토타입 체인 전체는 언제나 도달 가능하다. 화이트리스트가 실제로는 무력한데 진짜 보안 경계인 척했다면 플러그인 시스템이 아예 없는 것보다 더 나빴을 것이다 — 사실상 무제한인 코드 실행 주위에 거짓된 안전감을 심는 것이기 때문이다.

**개발 후 개선된 점:** 프런트엔드(Phase 4)와 백엔드(Phase 4.5)가 독립적으로 도달하고 문서화한 결론이 같았다: 화이트리스트는 실수 방지 장치이지 보안 경계가 아니며, 이 기능은 명시적으로 신뢰된 개발자·개발 환경 전용으로 스코프됐다 — iframe 샌드박스도 없고(기존 "JSX를 직접 반환" 패널 계약과 근본적으로 비호환), 백엔드 서브프로세스 격리도 없다(핫한 10Hz 파이프라인이 tick마다 IPC 왕복을 감당할 수 없음). 이게 플랫폼 전체에서 아마 가장 시니어급 엔지니어링 판단이 드러나는 결정일 것이다 — 그럴듯해 보이는 보안 기능이 실제로는 아무것도 지키지 못한다는 걸 정확히 짚어내고, 거짓된 안전감을 출시하는 대신 설계 문서에 그렇게 적었다는 점에서.

### 3.5 실제 MDF 구현 대신 의도적으로 단순한 커스텀 세션 녹화 포맷

**왜 필요했는가:** 원래 로드맵은 센서 히스토리를 실제 MDF4 산업 측정 포맷으로 export하도록 되어 있었다.

**안 했으면 생겼을 문제(실제로 발견된 것):** 실제 MDF4는 링크드 블록 그래프(IDBLOCK→HDBLOCK→DGBLOCK→CGBLOCK→CNBLOCK)에 deflate 압축 데이터 블록까지 필요하다 — 하나의 예시 플러그인으로 잡힌 스코프 대비 몇 주짜리 레퍼런스 구현 규모의 작업이었고, 이건 구현 중이 아니라 브레인스토밍 중 리서치로 발견됐다.

**개발 후 개선된 점:** 커스텀·처음부터 만든 `.sdfrec` 바이너리 포맷(단순 순차 헤더, 중첩 블록 없음)으로 방향을 틀었고, 언어에 무관하게 재구현 가능한 독립 스펙 문서를 함께 작성했다 — 절대 완전히 구현하지 않을 표준을 흉내내는 대신, 진짜 도메인 유용성(이 앱 자신의 센서 히스토리를 export)을 담았다. 이 피벗은 스케일 테스트 중 실제 버그도 하나 잡았다: `Math.min(...spread)` 호출이 2만5천 샘플 픽스처에서는 잘 작동했지만 픽스처를 37만5천 샘플로 키우자 스택 오버플로(V8의 spread 호출 인자 개수 제한)가 났다 — Worker 기반 파서의 논블로킹 가치를 실제로 보여주기 위해 픽스처를 일부러 키우기 전까지는 안 보이던 문제였다.

### 3.6 새 생성기를 만드는 대신 기존 모킹 데이터 로직을 발견해서 재사용

**왜 필요했는가:** 로드맵은 실제 백엔드 연결 없이 데이터를 재생할 수 있는 데모 모드를 요구했다.

**안 했으면 생겼을 문제:** 이미 존재하는 것(WebSocket 연결 끊김 시 자동 활성화되던, 문서화되지 않은 기존 사인파+가우시안 노이즈 시뮬레이터)이 있는데도 두 번째 병렬 모킹 데이터 생성기를 만들었다면, 유지보수해야 할 중복 로직이 생기고 둘이 어긋날 실제 위험이 있었을 것이다.

**개발 후 개선된 점:** 설계 단계에서 새 코드를 한 줄도 쓰기 전에 기존 생성기를 먼저 발견했고, 기능 전체가 "이미 존재하던 폴백 앞에 명시적 토글을 다는 것"으로 축소됐다 — 새 데이터 생성 로직은 0줄, `useWebSocket`을 관통하는 `demoMode` 플래그와 패널에서 그걸 토글하는 플랫폼 최초의 플러그인 쓰기 메서드(`setDemoMode`)만 추가됐다. 로드맵 설명만 보면 며칠짜리 빌드처럼 보이던 기능이, 가정하지 않고 실제 코드베이스 상태를 확인한 덕분에 타겟팅된 최소한의 변경으로 출시됐다.

### 3.7 발행형 npm 패키지 대신 로컬 스크립트로 만든 CLI 스캐폴드 생성기

**왜 필요했는가:** 기여자들이 보일러플레이트를 손으로 복사하지 않고 올바른 형태의 플러그인(컴포넌트 + 테스트 + 등록)을 빠르게 생성할 방법이 필요했다.

**안 했으면 생겼을 문제:** 진짜 `npx create-sdf-plugin` 패키지를 발행했다면, 오직 이 특정 모노레포 구조 안에서만 의미 있는 도구를 위해 독립적으로 버전 관리되는 두 번째 배포 아티팩트를 유지보수해야 했을 것이다.

**개발 후 개선된 점:** `pnpm create-plugin <name>`은 의존성 없는 로컬 스크립트로 컴포넌트·스모크 테스트를 생성하고 자동 등록까지 한다 — 기여자들이 실제로 일하는 방식(모노레포를 포크하지, npm에서 설치하지 않음)과 맞아떨어지고, 필요 없던 유지보수 표면을 피했다.

### 3.8 런타임과 하나의 에러 분류 경로를 공유하는 개발 전용 인스펙션 패널

**왜 필요했는가:** 기여자는 어떤 플러그인이 등록에 성공했는지, 실패했다면 왜인지 볼 수 있어야 한다 — 패널 ID 충돌, 렌더 에러, 백엔드 수집기 실패를 각각 다른 디버깅 워크플로로 쫓지 않고.

**안 했으면 생겼을 문제:** 서로 무관한 3개의 실패면(프런트엔드 패널 ID 충돌, 프런트엔드 렌더 에러, 백엔드 collector/pipeline 에러)을 임시방편 콘솔 로그로 디버깅했다면, 모든 기여자가 같은 디버깅 경로를 처음부터 다시 재발명했을 것이다.

**개발 후 개선된 점:** 레지스트리와 호스트의 패널 등록 액션 양쪽에서 던지는 공유 에러 클래스(`PluginPanelConflictError`) 하나로 `instanceof` 체크 한 번이 어디서든 실패를 올바르게 분류한다. 인스펙터 패널은 나중에(Phase 6) 같은 분류 경로에 꽂히는 렌더 에러·백엔드 에러 섹션을 얻었다 — 3개의 독립된 에러 리포팅 표면 대신 하나의 일관된 표면, `NODE_ENV`로 게이팅되어 실수로 프로덕션에 나갈 일이 없다.

## 3부 전체에 걸쳐 드러난 엔지니어링 실천

- **미봉책 대신 근본 원인 해결** — 커스텀 모델 카테고리 매핑(2.2)과 화이트리스트 위협 모델 결론(3.4) 둘 다, "당연해 보이는" 수정이 원래 문제보다 더 찾기 어려운 실패를 초래했을 사례이고, 둘 다 다음 사람이 재발견하도록 남겨두는 대신 명시적으로 문서화되어 있다.
- **만들기 전에 검증** — 데모 모드 발견(3.6)과 MDF 포맷 피벗(3.5) 둘 다 구현 코드를 쓰기 전 설계 단계에서 실제 코드베이스/도메인 현실을 확인한 데서 나왔고, 두 번 다 상당한 낭비를 미리 막았다.
- **자체 보고를 신뢰하는 대신 독립적으로 검증** — 2단계+홀리스틱 리뷰 프로세스(3.0)는 "단일 diff에 안 보이는 버그를 어떻게 잡는가"에 대한 의도적인 구조적 답이고, 9개 Phase·177개 커밋에 걸쳐 일회성 주장이 아니라 일관되게 적용됐다.
- **불확실성 앞에서 정직한 엔지니어링 커뮤니케이션** — "진짜 보안 경계가 아니다"라는 문서화(3.4)는 실제보다 더 안전한 것처럼 보이는 설계 문서 대신, 더 어렵고 덜 매력적인 결론을 선택해서 적은 것이다.
