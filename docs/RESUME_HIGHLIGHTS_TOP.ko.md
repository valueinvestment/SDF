# 이력서용 베스트 10 — SDF Digital Twin

이 프로젝트에서 가장 강력하고 방어 가능한 엔지니어링 결정 10개를 **XYZ 이력서 문장 공식**("**[Z]**함으로써 **[Y]**로 측정되는 **[X]**를 달성했다")에 맞춰 바로 쓸 수 있게 정리했다. 여기 안 담긴 나머지 9개 결정과 전체 맥락은 [`docs/RESUME_HIGHLIGHTS.ko.md`](./RESUME_HIGHLIGHTS.ko.md)에 있다.

**정직성에 대한 메모:** 아래 모든 숫자는 저장소에서 검증 가능한 값(테스트 수, 버그 수, 커밋 수)이거나 코드에서 직접 도출되는 기술적 사실(예: "리렌더 0회"는 코드상 위치 업데이트가 React 상태를 아예 건드리지 않는다는 사실에서 기계적으로 도출됨)이다. 매출·사용자 수·"몇 % 빨라짐" 같은 조작된 비즈니스 지표는 없다 — 이건 개인 포트폴리오 프로젝트이고, 면접관이 더 자세히 캐물으면 방어 못 할 숫자를 지어내는 건 역효과다. 숫자 대신 기술적 구체성 자체를 신뢰의 근거로 쓴다.

---

## 1. 리렌더 0회를 달성한 10Hz 실시간 위치 파이프라인

**초안 문장:** *`requestAnimationFrame` 렌더 루프가 직접 읽는 `useRef` 우회 경로로 업데이트를 라우팅해서, 10Hz로 갱신되는 실시간 위치 스트림에서 발생하는 React 리렌더를 전부 제거하고, 이중 렌더러(Three.js + React DOM) 대시보드가 연속적인 고빈도 업데이트에서도 매끄럽게 유지되도록 했다.*

- **X (무엇을):** 10Hz로 갱신되는 3D 시각화가 React UI 트리와 함께 있어도 매끄럽게 유지됨.
- **Y (측정 기준):** 위치 데이터로 인해 트리거되는 React 재조정 0회 — 코드상 기계적으로 검증 가능한 속성(위치 업데이트는 `useRef`에만 쓰고 `useState`/Zustand는 건드리지 않음)이며, 아키텍처 문서 성능 표에 측정된 특성으로 문서화되어 있음.
- **Z (어떻게):** "상태에 넣는다"는 표준 패턴이 10Hz 재조정 폭풍을 일으킬 걸 미리 식별하고, 애니메이션 루프가 직접 소비하는 ref 기반 우회 경로를 만듦.
- **왜 면접에서 강력한가:** 60초 안에 화이트보드로 설명 가능한 구체적이고 명확한 렌더링 성능 트레이드오프이고, "성능 최적화함"이라는 막연한 주장이 아니라 구체적 숫자(10Hz)와 구체적 메커니즘(ref 우회)이 있다.

## 2. 프로덕션 장애가 되기 전에 서버리스 타임아웃 충돌을 미리 인지하고 피함

**초안 문장:** *플랫폼의 10초 실행 상한이 애플리케이션의 Claude API 지연 예산과 정확히 충돌한다는 걸 파악한 뒤 서버리스 API 라우트 대신 영속 FastAPI 프로세스를 선택해서, 프로덕션에서 응답 도중 함수가 무작위로 종료되는 상황을 사전에 방지했다.*

- **X:** 발생하기 전에 프로덕션 신뢰성 장애 모드를 회피함.
- **Y:** 결과적으로 나온 아키텍처는 WebSocket 연결이나 계속 도는 10Hz 루프에 실행시간 상한이 아예 없다 — "제한선 아래 여유가 충분하다"가 아니라 그 제약 카테고리 자체를 제거한 것이다. 대안(Vercel의 10초 서버리스 상한)은 앱 자체의 Claude API 타임아웃 예산과 맞부딪혀 여유가 사실상 0이었다.
- **Z:** 제약에 맞추려고 밀리초를 깎는 대신, 아예 다른 플랫폼(Railway)에서 영속 프로세스를 돌려 제약 자체를 우회함.
- **왜 강력한가:** 사고 대응이 아니라 배포 *전에* 한 인프라 제약 추론을 보여준다 — 더 어렵고 더 가치 있는 역량이다.

## 3. 구독자별 큐로 느린 AI 지연을 실시간 브로드캐스트 루프에서 분리

**초안 문장:** *구독자별 전용 큐를 둔 pub/sub 이벤트 버스를 설계해서, 같은 이벤트 스트림에서 트리거되는 수 초짜리 AI 에이전트 체인이 10Hz 실시간 브로드캐스트 루프를 절대 지연시키지 못하도록 구조적으로 보장했다.*

- **X:** 같은 이벤트 경로에 있는 AI 추론 지연과 무관하게 실시간 데이터 스트림이 반응성을 유지함.
- **Y:** AI 체인(순차 Claude 호출 3번, 각각 수 초)이 독립된 태스크로 돌고, 브로드캐스트 루프의 주기는 아키텍처적으로 영향받지 않는다 — "대체로 괜찮다"가 아니라 구조적으로(구독자별 별도 큐) 증명 가능하게 분리됨.
- **Z:** 공유 알림 경로 대신 구독자마다 자기 큐를 갖는 `EventBus`를 만들고, 느린 소비자를 완전히 독립된 백그라운드 태스크로 돌림.
- **왜 강력한가:** 동시성/디커플링 설계는 전형적인 면접 주제인데, 이건 가상 시나리오가 아니라 실제로 출시된 사례를 준다.

## 4. 취약한 ID 접두사 매칭을 명시적 라우팅 레지스트리로 대체

**초안 문장:** *동적으로 생성되는 엔티티의 라우팅 근거를 ID 접두사 문자열 매칭(`startswith("M")`)에서 명시적 엔티티-카테고리 레지스트리로 옮겼다.*

- **X:** 타임스탬프 기반으로 동적 생성되는(고정 접두사 없는) 엔티티가 ID 문자열 형태에 의존하지 않고 올바르게 라우팅됨.
- **Y:** 모든 동적 생성 엔티티 ID가 이제 `sync_entities`로 채워지는 명시적 레지스트리를 통해 프런트엔드·백엔드 양쪽에서 해석된다. 기존 접두사 검사는 아직 동기화 안 된 엔티티를 위한 레거시 폴백으로만 남아있고, 주된 라우팅 메커니즘은 아니다.
- **Z:** 명시적 재조정 메시지로 채워지는 레지스트리를 도입해서, 앞으로 추가되는 새 엔티티 타입이 접두사 규칙을 맞추지 않아도 올바르게 라우팅되게 함.
- **왜 강력한가:** "취약한 패턴을 발견해서 구조적으로 견고한 것으로 교체했다"는 미드~시니어급 시그널이다 — 개별 버그가 아니라 버그 *클래스*를 생각한다는 걸 보여준다.

## 5. 거짓된 안전감 대신 정직하고 문서화된 보안 경계 판단을 내림

**초안 문장:** *런타임 동적 코드 로딩 기능의 보안 경계 후보로 플러그인 화이트리스트 API를 평가해서 신뢰할 수 없는 코드를 실제로는 격리할 수 없다(같은 JS realm에서 실행됨)는 걸 정확히 판단하고, 무력한 화이트리스트를 실제 보호처럼 포장하는 대신 이 기능을 신뢰된 개발자 전용으로 명시적으로 제한했다.*

- **X:** 보호하는 것처럼 보이지만 실제로는 아닌 보안 기능을 출시하는 걸 막음 — 이 프로젝트에서 가장 시니어급 판단이 필요했던 결정이라 해도 무방함.
- **Y:** 이 결론은 동적 플러그인 로딩의 프런트엔드(Phase 4)와 백엔드(Phase 4.5) 구현에서 각각 독립적으로 도달·문서화됐고, 둘 다 구현 시작 전에 자기만의 명시적 위협 모델 문서를 썼다.
- **Z:** 같은 realm의 `import()`가 실제로 뭘 접근할 수 있는지(호스트 JS realm 전체 — `window`, `document`, 프로토타입 체인) 끝까지 추적해서, 화이트리스트 객체로는 그걸 막을 수 없다는 결론을 내리고, 기능의 안전성을 부풀리는 대신 정직한 결론을 설계 문서에 그대로 적음.
- **왜 강력한가:** "어려운 기술적 판단을 내린 경험을 말해달라"는 질문에 가장 먼저 꺼낼 카드다. 보안 추론, "안전해 보이는" 기능을 출시하라는 압박 속에서의 지적 정직성, 명확한 기술 문서 작성 — 세 가지 시그널을 하나의 이야기에 담고 있다.

## 6. 외부 데이터 소스용 새 복원력 메커니즘을 만드는 대신 기존 패턴을 재사용

**초안 문장:** *신뢰할 수 없는 외부 데이터 소스(Modbus, OPC-UA, REST 폴링 같은 실제 기기 연동을 시뮬레이션)를 위한 결함 허용 데이터 수집 계층(오프라인 감지, 오래된 값 폴백, collector별 격리)을, 코드베이스에 이미 검증된 디커플드 폴링 패턴을 알아보고 확장해서 설계했다 — 두 번째로 어긋나는 복원력 메커니즘을 새로 도입하지 않고.*

- **X:** 외부 데이터 수집기가 전체 실시간 파이프라인을 멈추는 대신 우아하게 저하됨.
- **Y:** collector는 오프라인으로 표시되기 전까지 최대 3회 폴링 주기를 놓칠 수 있다(명시적이고 조정 가능한 임계값) — 그 전까지 소비자는 마지막 정상값을 보지, 오래된 에러 상태나 멈춘 대시보드를 보지 않는다.
- **Z:** 코드베이스에 이미 검증된 "느린 작업을 핫 루프에서 분리한다" 패턴(10Hz 메인 루프와 독립적으로 도는 2Hz 상세 스트림)이 있다는 걸 알아채고, 처음부터 새로 설계하는 대신 외부 collector에 *같은* 패턴을 확장함.
- **왜 강력한가:** 코드베이스 전반에 걸친 패턴 인식과 일관성 규율을 보여준다 — 모든 결정이 새로운 발명일 필요는 없다는 것, 언제 재사용해야 하는지 아는 것도 그 자체로 역량이다.

## 7. 소리 없는 종류의 안전 조치: 성능 회귀가 플러그인 생태계까지 번지기 전에 차단

**초안 문장:** *핵심 렌더링 성능 보장(메모이제이션된 스토어 구독을 통한 선택적 리렌더)을 서드파티 플러그인 API 표면까지 확장해서, 핵심 아키텍처가 애초에 막으려 했던 바로 그 성능 버그 클래스가 확장 경계에서 조용히 재발하는 걸 막았다.*

- **X:** 서드파티 플러그인이 이유를 몰라도 1st-party 컴포넌트와 동일한 렌더링 성능 보장을 자동으로 받음.
- **Y:** 한 데이터 슬라이스를 구독하는 플러그인이 무관한 10Hz 스토어 업데이트에서는 리렌더되지 않는다 — 1번 항목과 같은 "불필요한 리렌더 0회" 속성이, 이번엔 플러그인 작성자가 통제할 수 없는 경계에서 강제됨.
- **Z:** 플러그인에 노출되는 *유일한* 스토어 접근 API로 `useSyncExternalStore`를 선택자 기반 깊은 동등성 메모이제이션으로 감싸서, 플러그인 작성자가 실수로 10Hz 리렌더 폭풍을 재도입할 가능성 자체를 차단함.
- **왜 강력한가:** 시스템 사고를 보여준다 — API 경계가 정확히 이미 해결된 문제가 조용히 재발할 수 있는 지점이라는 걸 인식하고, 미래의 모든 플러그인 작성자가 더 잘 알기를 믿는 대신 구조적으로 막았다.

## 8. 모든 Phase에서 실제 비직관적 버그를 잡아낸 2단계 + 홀리스틱 코드 리뷰 프로세스를 구축·운영

**초안 문장:** *9-Phase, 177커밋 규모의 플랫폼 구축 전체에서 모든 구현 태스크에 필수 2단계 리뷰(스펙 준수 → 코드 품질)를, Phase마다 최종 전체-브랜치 홀리스틱 리뷰를 추가로 시행해서, 개별 태스크 리뷰만으로는 놓쳤을 실제 결함들 — 개별 diff로는 안 보이는 태스크 간 버그 1건 포함 — 을 잡아내고 고쳤다.*

- **X:** 9-Phase 플랫폼 구축 전체에서 실제 결함을 잡아내고 고쳤다 — 개별 태스크 리뷰로는 절대 볼 수 없었던, 두 태스크의 코드가 *상호작용*할 때만 존재하는 태스크 간 버그 1건 포함.
- **Y:** 3개 실패 분기 중 2개만 커버하던 부분적 롤백 경로(Phase 3a), 첫 번째 잘못된 입력에서 백그라운드 로더를 조용히 죽였을 형태 검사 누락(Phase 4.5), 그리고 룰의 대상을 편집 도중 재지정해도 이미 입력된 조건식이 재검증되지 않던 Phase 5b의 데이터 정합성 버그 — 전부 머지 전에 발견·수정됐고, 마지막 것은 개별 태스크가 전부 자기 리뷰를 통과한 뒤 최종 전체-브랜치 리뷰에서만 잡혔다.
- **Z:** 모든 태스크가 독립적인 스펙 준수 확인(구현자의 자체 보고를 신뢰하는 대신 diff를 다시 읽음)을 통과한 뒤 코드 품질 확인을 거치도록 요구했고, 모든 개별 태스크가 통과한 뒤에도 *전체* 브랜치 diff에 걸친 리뷰 패스를 하나 더 추가해서 단일 태스크 시야로는 못 잡는 걸 잡아내도록 함.
- **왜 강력한가:** 2026년 기준 "AI 보조 개발을 어떻게 책임감 있게 쓰는가"는 점점 더 흔해지는 면접 질문이다 — 이건 구체적이고 정량화된 답이다: 생성된 코드를 맹신하지 않는 검증 규율, 그리고 넓은 시야의 리뷰 레이어만 잡을 수 있는 특정 버그 클래스(태스크 간 상호작용)의 구체적 사례.

## 9. 리서치로 비현실적인 요구사항을 축소한 뒤, 그 결과 설계에서 실제 스케일링 버그를 잡음

**초안 문장:** *업계 표준 MDF4 바이너리 포맷을 구현하라는 로드맵 요구사항을 조사해서(시행착오식 구현이 아니라 리서치로) 단일 예시 기능치고는 몇 주짜리 레퍼런스 구현 규모의 작업이 필요하다는 걸 파악하고, 대신 목적에 맞게 설계한 대체 포맷을 만들었다 — 그리고 그 결과물의 스케일 테스트 중 실제 V8 스택 오버플로 버그(`Math.min(...spread)`)를 잡았다.*

- **X:** 구현 *전에* 실현 가능성을 조사해서 몇 주짜리 스코프 초과를 피했고, 별개로 의도적인 스케일 테스트를 통해 실제 프로덕션급 버그를 잡음.
- **Y:** 포맷 복잡도 발견(링크드 블록 그래프 + 압축 데이터 블록)은 구현 코드를 한 줄도 쓰기 전에 기능 전체 설계를 바꿀 만큼 구체적이었다. 스택 오버플로 버그는 2만5천 샘플 테스트 규모에서는 안 보였고 테스트 픽스처를 실제 부하를 제대로 검증하기 위해 의도적으로 37만5천 샘플로 키운 뒤에야 드러났다 — V8의 spread 호출 인자 개수 상한이 그보다 훨씬 낮은 지점에 있다.
- **Z:** 구현 중간에 스코프 문제를 발견하는 대신 설계/브레인스토밍 단계에서 실현 가능성 리서치를 했고, "현실적인 규모에서도 이게 여전히 동작하는가"를 작은 픽스처가 대표성 있다고 가정하는 대신 의도적인 테스트 차원으로 다뤘다.
- **왜 강력한가:** 하나의 이야기에 두 가지 서로 다른 엔지니어링 미덕이 담겨 있다 — 스코핑 판단력("정확하지만 과도한" 해결책 대신 더 단순하고 목적에 맞는 해결책을 만들 때를 아는 것)과 엄격한 테스트 규율(작은 픽스처 테스트로는 못 잡는 걸 스케일 테스트가 잡음).

## 10. 문서화되지 않은 기존 기능을 발견해서 중복 구현 대신 재사용

**초안 문장:** *설계 리서치 중, 요청받은 "데모 모드" 기능의 핵심 데이터 생성 로직이 이미 문서화되지 않은 모킹 데이터 생성기로 존재한다는 걸 발견하고, 두 번째로 중복되는 데이터 생성 시스템을 만드는 대신 최소한의 명시적 토글 추가로 기능을 출시했다.*

- **X:** 원래 스코프됐던 구현 작업의 일부만으로 로드맵 기능을 배포함.
- **Y:** 새 데이터 생성 로직은 0줄 작성됐다 — 기능 전체가 하나의 훅을 관통하는 불리언 플래그 하나 + UI에서 그걸 토글하는 새 플러그인 쓰기 메서드 하나로 축소됐다, 로드맵 설명이 암시했던 "처음부터 생성기를 만드는" 작업 대비.
- **Z:** 구현 코드를 쓰기 전 설계 단계에서 실제 현재 코드베이스 상태를 확인했다 — 로드맵의 표현("...하는 모드를 만든다")이 아직 아무것도 없다는 뜻이라고 가정하지 않고.
- **왜 강력한가:** "재고 두 번, 절단 한 번"의 구체적 사례다 — 구현 노력을 투자하기 전에 가정을 현실과 대조해서 검증하는 것, 단순히 빠른 것보다 성숙함으로 읽힌다.
